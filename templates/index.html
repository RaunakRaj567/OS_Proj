        Resolution Strategies

        Prevention makes deadlock impossible by ensuring that at least one of the four necessary conditions can never hold. Each protocol below is applied to a copy of the current state and re-checked by the detection engine.

        Avoidance needs each process's maximum claim in advance (edit it in the Max tab of the Control Deck). A request is granted only if the system stays in a safe state, i.e. a safe sequence exists. Banker's algorithm: Need = Max − Allocation.

        Safe sequence

        Need = Max − Allocation

        State space

        Safe ⇒ no deadlock. Unsafe ⇒ deadlock is possible. Every deadlocked state is unsafe.

        Resource-request algorithm

          The tool suggests strategies that match what it detected. For an actual deadlock it offers recovery (terminate, preempt, roll back). For a potential deadlock it offers mitigation (enforce an acquisition order, restore a safe state). Every strategy is simulated on a copy of the system and verified by the detection engine.

          No deadlock and no risk → nothing to resolve. ✔

          Starvation is indefinite postponement: the system makes progress but one process never does. In recovery, if the same process is always the cheapest victim it can be rolled back forever. Fix: aging, counting how often a process was chosen in its cost factor.

          Victim history · this session

          Each time you apply a recovery, its victims are recorded here. Each previous selection adds 60 to that process's victim cost, and after 3 selections it is protected.

          Where else starvation appears

          • Hold-and-wait prevention: a process needing several popular resources at once may wait indefinitely.
          • Resource preemption / rollback: the same victim may be preempted again and again.
          • Deadlock vs starvation: in a deadlock no process in the set progresses; with starvation the others keep running.
